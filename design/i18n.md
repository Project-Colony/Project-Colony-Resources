# Internationalization

**English is the base language of every Project Colony project.** Source code,
identifiers, comments, commit messages, README and `docs/` are English; see
[documentation.md](documentation.md).

Localization sits on top of that: a program's **user interface** ships in
English and French. The English string is the canonical one: it is what the key
is named after and what a new key is written in first. The French string is a
translation of it, and it is not optional: both locales ship complete, and a
test fails when one is missing.

So the page whose `settings_title` is `Preferences` in English and `Préférences`
in French is *the Preferences page*. Refer to it by its English name everywhere
except in the French locale file itself.

## The rules

1. **Every user-visible string goes through the i18n layer.** A literal in a
   widget is a string that will never be translated and that nobody will find
   later.
2. **A key exists in both locales or in neither.** Colony enforces this with a
   test (`fr_and_en_have_identical_key_sets` in `src/i18n/mod.rs`), and so does
   the generator here for every shared label. Adding a key to one file and
   forgetting the other fails the build, on purpose.
3. **A key reused across contexts carries the same string everywhere.** This one
   is enforced here: the generator refuses to emit labels if a key like
   `settings_theme_light` appears with two different values.
4. **Proper nouns stay untranslated.** Theme families are brands (Catppuccin,
   Gruvbox, Kanagawa, Stellar Blade) and they read identically in both files.
   Character names likewise: EVE is EVE. So do font names: OpenDyslexic.

A program sets the locale once at startup, from its own language preference or
the environment, and the shared labels follow it:

```rust
colony_ui::i18n::set_locale(colony_ui::i18n::Locale::from_tag(&language));
```

## Naming keys

The pattern in use, worth keeping:

```
settings_cat_<category>        settings_cat_appearance
settings_<category>_desc       settings_appearance_desc
settings_section_<section>     settings_section_vision
settings_<section>_desc        settings_vision_desc
settings_<setting>             settings_high_contrast
settings_<setting>_desc        settings_high_contrast_desc
settings_theme_<family>        settings_theme_kanagawa
settings_theme_<family>_<var>  settings_theme_stellar_blade_eve
settings_accent_<name>         settings_accent_violet
```

Shared variant labels are deliberately generic so they can be reused: a dozen
families share `settings_theme_light` and `settings_theme_dark_mode` rather than
each declaring their own "Light". Only give a variant its own key when it has a
real name: `settings_theme_rosepine_moon`, `settings_theme_monokai_spectrum`.

The `settings_` prefix is a key convention, never something the user reads: the
values say Preferences. A program's own new keys follow
[navigation.md](navigation.md) and use `preferences_*`, so they cannot collide
with the shared table.

## Labels owned by this repo

Two kinds of label live in `tokens/` and are generated into `colony-ui`:

- the names of the shared design objects, next to the colours they name: theme
  families and variants in `tokens/families/*.toml`, accents in
  `tokens/accents.toml`;
- the shared interface strings of the Preferences skeleton, in
  `tokens/labels.toml`: the page title, Close, the three mandatory categories
  and About with their descriptions, and every Appearance and Accessibility
  control the kit draws, with its description.

Both are emitted to:

```
crates/colony-ui/src/generated/labels.fr.json
crates/colony-ui/src/generated/labels.en.json
```

with identical key sets, verified by the generator before the files are written
and by `cargo test` after. A program reads them with `colony_ui::i18n::t`, or
merges `colony_ui::i18n::all(locale)` into its own table. It does not copy them
into its own locale files: a copy is how two strings for one object start to
drift.

Everything else stays in the consuming program: its own categories (Storage,
Audio), its own sections (Startup, Updates), its button text. This repo owns the
strings of what every program shares, not each program's vocabulary.

## Adding a language

Not planned, and the current model does not accommodate it: `Label` has exactly
an `fr` and an `en` field, and that is deliberate. A `HashMap<locale, String>`
would let a locale be silently incomplete, which is the failure mode both tests
above exist to prevent. Adding a third locale means widening `Label` and
`UiLabel` in `tools/colony-tokens/src/model.rs` and extending the parity check
to cover every locale, not relaxing it.

## Writing the strings

- **Write the English first.** It is the canonical string and the one the key is
  named after. A French string invented first and translated outward produces
  English that reads like a translation, which is the wrong way round.
- **The French is not a gloss.** Write it as French: "Mode sombre", not
  "Sombre mode". A translated key still has to sound like something a French
  speaker would have written.
- Descriptions explain the consequence of a setting, not its name a second time.
- **Budget for French being longer.** It runs roughly 15-20% longer than
  English, so a layout that only just fits the English string will break in
  French. Check the wider locale before calling a screen done.
