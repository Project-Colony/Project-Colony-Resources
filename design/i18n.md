# Internationalization

Colony ships **French and English**, and both are first-class. Not "English with
a translation" — two locales that must stay in step.

## The rules

1. **Every user-visible string goes through the i18n layer.** A literal in a
   widget is a string that will never be translated and that nobody will find
   later.
2. **A key exists in both locales or in neither.** Colony enforces this with a
   test — `fr_and_en_have_identical_key_sets` in `src/i18n/mod.rs`. Adding a key
   to one file and forgetting the other fails the build, on purpose.
3. **A key reused across contexts carries the same string everywhere.** This one
   is enforced here: the generator refuses to emit labels if a key like
   `settings_theme_light` appears with two different values.
4. **Proper nouns stay untranslated.** Theme families are brands — Catppuccin,
   Gruvbox, Kanagawa, Stellar Blade — and they read identically in both files.
   Character names likewise: EVE is EVE.

## Naming keys

The pattern in use, worth keeping:

```
settings_<category>            settings_cat_appearance
settings_section_<section>     settings_section_theme
settings_theme_<family>        settings_theme_kanagawa
settings_theme_<family>_<var>  settings_theme_stellar_blade_eve
settings_accent_<name>         settings_accent_violet
```

Shared variant labels are deliberately generic so they can be reused: a dozen
families share `settings_theme_light` and `settings_theme_dark_mode` rather than
each declaring their own "Light". Only give a variant its own key when it has a
real name — `settings_theme_rosepine_moon`, `settings_theme_monokai_spectrum`.

## Labels owned by this repo

Theme and accent labels live in `tokens/`, next to the colours they name, and are
emitted to:

```
generated/i18n/labels.fr.json
generated/i18n/labels.en.json
```

54 keys per locale as of the import, with identical key sets — verified by
`cargo test` before the files are written.

Everything else — section titles, descriptions, button text — stays in the
consuming program. This repo owns the strings that name the shared design
objects, not the whole UI vocabulary.

## Adding a language

Not planned, and the current model does not accommodate it: `Label` has exactly
an `fr` and an `en` field, and that is deliberate — a `HashMap<locale, String>`
would let a locale be silently incomplete, which is the failure mode both tests
above exist to prevent. Adding a third locale means widening `Label` in
`tools/colony-tokens/src/model.rs` and extending the parity check to cover every
locale, not relaxing it.

## Writing the strings

- French is not a gloss of the English. Write it as French — "Mode sombre", not
  "Sombre mode".
- Descriptions explain the consequence of a setting, not its name a second time.
- Keep both locales roughly the same length. French runs ~15–20% longer than
  English; a layout that only fits the English string will break in French, and
  French is the locale the ecosystem's author actually reads.
